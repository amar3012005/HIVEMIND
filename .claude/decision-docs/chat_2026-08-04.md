## 2. Backend fixes

### D1 — Tool results were truncated blind, mid-row
**Symptom.** Chat answered "the record doesn't include that" about content it had just
retrieved. 4/6 on the canary.

**Cause.** A flat `slice(0, 8000)` on the tool result, cutting **mid-row**, so the answer model
received a fragment of the last memory — syntactically broken and semantically misleading.

**Decision.** Per-row budgeting with `AGENT_TOOL_RESULT_MAX_CHARS` (default 24 000): rows are
included whole or not at all, so the model never sees half a memory. Canary 4/6 → **6/6**.

**Note on my own testing.** I first reported a "wrong answer" from chat that was my probe's
fault — I had omitted the keyword the canary sends and `stream:false`.

### D2 — A recall timeout was presented as "nothing exists"
The single most serious defect touching chat. Full detail in `recall_2026-08-04.md` D1; the
chat-side half:

`execBaseRecall` catches its own deadline rejection and returns `null`, so a timed-out hop
contributes nothing — **indistinguishable from an empty workspace**. The answer path then chose
`unavailableEvidenceResponse`'s "doesn't appear in any source so far" branch and asserted a
**false negative as fact**.

**Decision.**
- `gatherEvidence` derives `coverage.retrieval_timed_out` from the **steps actually executed**,
  the same way `answer_mode` is derived — reporting what happened, never what was planned.
- `unavailableEvidenceResponse` gains a timeout branch (de/fr/es/en) that says the lookup was cut
  off and to ask again — *which is what actually works* — instead of claiming absence.
- The retrieval budget was raised 3 000 → 12 000 ms, since 3 000 was below this system's own cold
  recall latency (~2 600 ms).

This mirrors `sourceUnavailableResponse`, which already distinguished "could not retrieve" from
"not present". The timeout case was simply missing from that idiom.

### D3 — `scopes_found` covered only one lane
**Requirement.** Chat shows "(memory found in <scope>)" so tenant scoping is visible per turn,
mirroring the Memories page for **any** user (no company-specific behaviour).

**Genuine gap.** `scopesFound` iterated only `evidence.memories`. An answer built purely from
`knowledge_segments` — exactly what a KB-upload question hits — has an empty `memories` **by
design**, so those turns showed no provenance at all.

**Decision.** Evidence rows now carry `scope` (via `documentScopeFromTags`, see
`recall_2026-08-04.md` D3) and `scopesFound` unions both lanes in one loop. Project ids still
resolve to names in a single batched read, so the chip reads `project:SOLVIS`, not a uuid.

**What I got wrong first.** I twice root-caused this as (a) `evidence.memories` never populated
on the tool path and (b) `scope` not hydrated. **Both false** — `mapMemoryRecord` and
`mapAgentRow` both stamp `scope`, all 776 memories in the test org have it, and `scopesFound` *is*
computed on the recall path's only user-facing return. The returns that omit it are
connector-write turns that retrieve nothing, where `[]` is correct.

### D4 — Quota enforcement confirmed on the consuming path
Not a fix — a **verification** that closes a standing question ("is the limit *called* on the
consuming path, or merely defined?").

Repeated test uploads produced:
```
HTTP 402 {"error":"plan_limit_exceeded","message":"Monthly upload limit exceeded
 (Free plan: 10 uploads/month)","resource":"uploads","limit":10,"current":11,
 "suggested_plan":"pro","upgrade_url":"/hivemind/app/billing"}
```
Enforced, with an actionable body and an upgrade path. Working as designed.

## 3. Frontend fixes

### D5 — "Only the top 4 upload and then it stops"
**Reported symptom.** Four files upload; everything else sits untouched; the page looks frozen.

**Two causes, one fatal.**
- `pickConcurrency` caps at 4 for files under 5 MB — by design, to protect the Prisma pool.
- **The killer:** `uploadDocument` posts the bytes and *then polls to completion*, so the worker
  loop's `await uploadOne(...)` **pinned one of those 4 slots through the entire server-side
  ingest.** The logs show what that costs: `promote=134118ms`, `extract=118173ms`. One document
  held a slot for over two minutes.

The server already has its own BullMQ `kb-queue` (cap 6) — the real throughput limit — so a
second client-side gate on **processing** protected nothing and destroyed the appearance of
progress.

**Decision.** `api-client` fires a new `onQueued` callback the instant the POST returns a
`job_id`; the worker waits on **that** instead of on completion. The ingest keeps running and
reporting; every one is still awaited before the batch is considered done. Byte upload now
returns in **80 ms**.

Care taken: rejections cannot escape the worker (an unhandled one would strand the rest of the
queue), and the retry path passes the **same** entry object rather than a fresh literal — a copy
would lose `_slotReleased` and the retry could never free its slot.

### D6 — The flicker: two writers racing on one field
**Reported symptom.** "FE is just flicking, confusing to watch."

**Cause.** `onStatus` set the real server phase (`parsing → embedding → promoting`), and then
`onUploadProgress`'s timer overwrote `stage: 'processing'` **every 500 ms**. Both the progress bar
*and* the percentage/speed/ETA were chosen by `stage === 'processing'`, so each row alternated
twice a second between a determinate 100 % bar showing a **stale upload speed** and an
indeterminate pulse — for the whole ingest. The accurate phase was already arriving; the timer
was destroying it.

**Decision — one owner per field.**
| field | owner |
|---|---|
| `progress`, `bytesDone` | the byte transfer |
| `stage`, `stageLabel` | the server, via `onStatus` |
| `processingSec` | a fallback counter, **only** until the first server phase arrives |

Both bars are now keyed off the single fact `bytesDone`, so they are mutually exclusive and a row
can never satisfy neither. Transfer stats render only while the transfer is live, so
"100 % · 4.2 MB/s · eta 0 s" can no longer sit next to "Extracting memories" minutes after the
upload finished. Retry resets `bytesDone`/`progress`, since a retry re-sends from zero.

### D7 — Two different "queued" states looked identical
`status:'queued'` means the file has not been sent yet (waiting for a client slot); the server's
own `queued` stage means it **is** sent and waiting for a worker. The first rendered as a bare
clock icon, the second as "Queued — waiting for a worker" — so a file that had not started looked
identical to one already server-side. The client-side case now says **"Waiting to upload…"**.

### D8 — The 501 on the Memories page
**Reported.** `GET /v1/proxy/admin/contradictions?limit=1` → `501` with
`{"storage_mode":"amr","supported":false,"error":"not_supported_for_amr_storage"}` for org
`6946c8a6`.

**The server was right.** That endpoint reads the **central graph**; an org whose memories live
on its own `.amr` agent has no rows there. Refusing is correct — it declines rather than
reporting a misleading zero. The page was never broken either: a `.catch(() => ({ data: null }))`
was already there.

**What was wrong** is that the request still fired on every load, giving every `.amr` tenant a red
console error and a wasted round trip.

**Decision.** Gate the call on the `storage_mode` that `/memory/stats` **already publishes**, so
it only runs where it can succeed. Any non-`amr` value — including an older core that omits the
field — keeps the previous behaviour.

Plus one line of UI: skipping silently would leave the contradictions panel simply **absent**,
which reads as "no conflicts found" — the same misleading zero the server refused to give. It now
says conflict detection is unavailable for this workspace, and why.

**`deploy-fe.sh` no longer does `git reset --hard`.** My prior knowledge was stale: lines 25–33
document that it was replaced with a **throwaway worktree off a named, pushed commit**. So a

**But it deploys `hm-feature (:8088)`, which is NOT what the user sees.**
`next.singulancelabs.com` → `localhost:2388` → **`hivemind-next-frontend-1`**, a different
container in the `hivemind-next` compose project, pinned by a three-line override at
`/tmp/hm-tara-frontend-override.yml`. I caught this by reading the Caddyfile rather than assuming,
after `deploy-fe.sh` reported success on a container nobody was looking at.

**Concurrency with another session.** That served container was re-pointed **three times** by a
parallel session while this work was in progress (`sha-b2052b2e` → `bf7af3ca` → `951d64b4`).
Before superseding each, I verified ancestry rather than assuming:
- `b2052b2e` is a **hivemind-repo** commit whose `frontend/Da-vinci` gitlink was `f508b3b` — the
  exact parent of my FE commit, so superseding it lost nothing;
- `bf7af3ca`'s gitlink `be7021c` **contains** my `ff62d4cc2`, so their deploy preserved my fix.

**Verification that counts.** Not "container restarted" but **markers in the served bundle**.

## 5. What chat still cannot do well

### The language leak reaches chat
~67 % of extracted facts are translated out of the source language
(`kb_ingestion_2026-08-04.md` D8). Chat therefore answers a German question from English
memories. Retrieval still finds them (the cross-encoder is language-tolerant), but the *rendered
answer* mixes languages, and a user reading their own document's facts sees them rewritten.
**Measured, unfixed.**

### The cross-lingual flap is not chat's fault
Four identical runs returned identical retrieval ID sets; all relevant temperatures are 0; zero
failover events in 6 h. The residual variance is provider-level non-determinism at temperature 0
on an MoE model. Levers: `seed` on the answer call, or a stronger answer model. Both A/B
decisions.

## 9. Invariants for the next session

- **A failed lookup must never render as "nothing found."** This is the defect shape that keeps
  recurring: `200 []`, `indexed` with zero memories, an empty Memories page on a locked shard.
- **One owner per state field.** Two writers on `stage` produced a 2 Hz flicker for the entire
  ingest; the accurate value was already there.
- **Bound a client queue on the transfer, not on server processing.** The server has its own
  queue; a second gate only hides progress.
- **Verify the container the URL actually resolves to** — read the Caddyfile, don't infer from a
  deploy script's success message.
- **Verify FE fixes in the served bundle, and search every chunk.** Route code is code-split.
- **Check ancestry before superseding another session's release**, in both directions.
