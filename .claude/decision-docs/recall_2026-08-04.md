## 2. What was fixed

### D1 — A recall timeout was reported to the user as an absence
**The defect, in the user's own transcript.** A question whose answer *was* in the workspace
returned: *"I don't have anything in my memory about that yet — … doesn't appear in any source
so far."* The identical question seconds later returned **5 memories + 8 evidence** and answered
correctly.

**Three causes, all fixed in `90e04f41`.**

**(a) The budget was below this system's own measured latency.**
`HIVEMIND_AGENT_RETRIEVAL_BUDGET_MS` defaulted to **3 000 ms**. Measured on this box: a cold
recall runs to ~2 600 ms (keep-warm puts the warm floor near 640 ms, which is remote-Qdrant-bound),
and evidence retrieval alone measures 258–967 ms warm. A cold turn therefore had ~400 ms of
headroom for **every hop combined**. Raised to **12 000 ms**; `TURN_BUDGET_MS` (60 s) still
bounds the worst case.

> Verified `HIVEMIND_AGENT_RETRIEVAL_BUDGET_MS` is **not** set in the live env — otherwise the
> code change would have been inert. This check is not optional; see `kb_ingestion` D6/D10.

**(b) The deadline miss was invisible downstream.** Each hop catches its own deadline rejection
(`execBaseRecall`'s `catch` records `error: recall deadline exceeded` and returns `null`) and
contributes nothing — indistinguishable from "the workspace holds nothing".
**Decision:** `gatherEvidence` derives `coverage.retrieval_timed_out` from the **steps actually
executed** (the same way `answer_mode` is derived), so the distinction survives to the answer.

**(c) The reply now tells the truth.** `unavailableEvidenceResponse` says the lookup was cut off
and invites a retry — *which is what actually works* — instead of asserting the topic appears in
no source. The codebase already had this idiom in `sourceUnavailableResponse` ("could not
retrieve" ≠ "not present"); the timeout case was simply missing from it.

**Why this is the most serious recall defect of the session:** a false negative asserted as fact
is the same shape as a document logged `indexed` with zero memories, or `200 []` from a broken
dependency. The user cannot distinguish "nothing stored" from "lookup failed".

### D2 — Embedding failover: a dead primary cost 30 s on *every* call
**Symptom.** `⚠️ Embedding primary failed, falling back: LiteLLM embedding timeout after
30000ms`, and a single recall measured at **30 616 ms** while the fallback was healthy and
answering.

**Cause.** `FallbackEmbedService` tracked `_primaryHealthy` and then used it **only to decide
whether to log**. The primary was still awaited first every single time. With
`EMBEDDING_TIMEOUT_MS=30000` and no client-side retry, one unreachable primary added 30 s to
every embedding call — and every vector lane depends on it.

**Decision (`00c2380c`).** An **ordered chain** replacing the two-link wrapper:
- a failed link is **deprioritised** for `EMBEDDING_LINK_COOLDOWN_MS` (60 s) — measured after
  the fix: **5 consecutive calls with a dead primary take 0 ms and attempt the primary once**;
- cooldown **deprioritises, never removes** — a cooled-down link moves to the back and is still
  tried last, so "slow" can never become "no embedding at all";
- **any number of links**: `EMBEDDING_FALLBACK2_PROVIDER` adds a third, and OpenRouter
  `baai/bge-m3` is appended as a **terminal** last resort (a managed multi-provider endpoint does
  not share a failure domain with a self-hosted GPU box). When the terminal link is omitted, the
  **reason is logged** rather than left silent.

**The correctness point that governs the design.** *Same dimension is not same vector space.*
bge-m3 on two hosts is interchangeable; bge-m3 and mistral-embed are both 1024-dim and are
**not**. Mixing spaces raises no error — it silently returns nonsense neighbours, which is worse
than a failed embedding. So a dimension mismatch is logged loudly, and an all-links-down call
**throws** rather than returning a zero or partial vector that would be indexed as real.

**On the user's request** ("add a secondary fallback embedding model so it never fails"):
bge-m3 was **already** the configured fallback (`EMBEDDING_FALLBACK_PROVIDER=openrouter`,
`OPENROUTER_EMBED_MODEL` defaulting to `baai/bge-m3`, 1024-dim). The model was not missing; the
chain around it was weak. A chain of one is returned bare, so single-provider deployments are
unchanged.

**Live proof:** the identical probe went **30 616 ms → 967 ms**, then 258 ms warm. Boot log
reads `[embed] chain: litellm -> openrouter (dim=1024)` with no mismatch warning, and zero
embedding failures in the 25 minutes after deploy.

### D3 — Evidence carried no scope, so provenance was invisible
Segments have no scope column (`knowledge_segments` holds only `document_id/user_id/org_id`), so
the tier lives in `knowledge_documents.tags` as `scope-key:*`.

**Decision (`1208a37a`).** One helper, `documentScopeFromTags`, reusing the tag forms
`_accessibleDocumentWhere` already matches — including the
`scope-key:org:<uuid>` / legacy `scope-key:organization` pair. `tags` was not even selected
before; it is now fetched and **stripped from the emitted payload** so citations do not grow.

Untagged ⇒ `personal`, which is **not a guess**: untagged documents *are* owner-only via
`_accessibleDocumentWhere`'s bare `{ userId }` arm.

8/8 cases, including the one that matters for tenancy: **an org tag belonging to a *different*
org does not read as `organization`** — it fails closed.

**Verified live on both lanes:** `retrieveEvidence` for org `1380251c` returned 6–8 segments
across vector **and** lexical, every row carrying `scope`, `tags` confirmed not leaking. Project
tier verified separately against org `807ebb88`: `scope=project` with the correct `project_id`.

### D4 — `.amr` reads: two defects behind one symptom
Both in `3185410a`; full detail in `kb_ingestion_2026-08-04.md` D13/D14. Recall-relevant summary:

- **Shard "locked by another process" was hm-core fighting itself.** `getCtx` awaited
  `ensureSchema()`/`ensureQdrant()` *before* caching, so concurrent callers for one org both
  opened the shard; the lock is per-**open**, not per-process. `fuser` proved a single PID held
  every `shard.lock` with hm-core's own main PID as parent. Fixed with **single-flight** on the
  in-flight promise. Verified: **12 concurrent requests → 1 shard open, 0 lock errors.**
- **A failed read returned an empty list.** `remoteList` caught everything and returned
  `{ memories: [] }`, so a transient lock collision rendered a tenant's Memories page **empty** —
  indistinguishable from having no memories. It now throws; user-facing reads propagate,
  background jobs (`profile-dreamer` ×2, `cognition-loop`) opt into tolerance with a logged
  `.catch`.

### D5 — Chat tool results were truncated blind (recall's output, wasted)
`react-agent-v2.js` sliced tool results at a flat `slice(0, 8000)`, cutting mid-row so the
answer model saw a fragment of the last memory. Replaced with **per-row budgeting**
(`AGENT_TOOL_RESULT_MAX_CHARS`, default 24 000). Detailed in `chat_2026-08-04.md` D1 — recorded
here because it is recall output being destroyed after successful retrieval.

## 3. What was measured and deliberately NOT shipped

### R1 — Trigram lexical matching: rejected on evidence
The plan (`recall_final.md` lineage) justified trigram with the vocabulary-mismatch case
`Artikelnummer` vs `Art.-Nr.`. Measured on live data, org `1380251c` (3 102 segments):

| variant class | `word_similarity` | vs 0.4 threshold |
|---|---|---|
| `Teillast` → `Teillastbetrieb` | 0.889 | passes |
| `Umbausatz` → `Umbau` | 0.500 | passes |
| `Ladesaeulen` → `Ladesäule` | 0.417 | passes |
| **`Artikelnummer` → `Art.-Nr. 35113`** | **0.214** | **fails** |

**It does not fix the case it was proposed for**, at any usable threshold.

Cost, `EXPLAIN ANALYZE` on live:
- per-token indexable `%>` form: **246 ms** — the planner chooses Seq Scan, correctly: the
  `gin_trgm_ops` index is on `content` alone while 2 663 of 3 102 rows match the org filter;
- 4 tokens via `unnest` cross join: **866 ms**.

The lexical pass sends up to 16 tokens, against a 2 s recall budget.

And its unique coverage is narrower than assumed, because the **existing `contains` pass already
covers the prefix direction**: `ILIKE '%Teillast%'` returns **13** segments including
`Teillastbetrieb`. Trigram uniquely adds only (a) query term longer than the document term and
(b) umlaut transliteration. Noise is real too: `word_similarity('Artikelnummer', …) > 0.4`
returned 5 rows, 3 of them `"Artikel in Fachzeitschriften"` (magazine articles).

**Decision: not on the hot path.** If wanted, it belongs in a **precomputed umlaut-folded
column with its own index, populated at ingest** — then it costs an index probe, not 246 ms of
`word_similarity` CPU per token.

**A correction I owe the record:** I first claimed "the central evidence lane is vector-only".
It is not. The block at `evidence-retrieval.js:319` states in its own comment *"ALWAYS additive
(not only when vector is sparse)"*. I had written a **second** lexical lane before noticing, and
reverted it — that would have been exactly the duplication this codebase forbids. Trigram *is*
also already active in the **memory** lane (`prisma-graph-store.js:~1196`,
`public.word_similarity(...) > 0.4`, ungated), which I had earlier said it was not.

### R2 — Cross-lingual answer flap: proven NOT a retrieval bug
**Symptom.** An English question against German source text intermittently returned a less
specific answer (the `E3DC` case).

**Measurement.** Four identical runs returned **identical ID sets**
(`5ef9536c, 786f1274, 2dfa4a9f, 48c3dd71, 55f9295c`) with `E3DC_occurrences=1` **every** run.
Temperatures confirmed 0 on the intent classifier, synthesis, tool loop and progressive router
(only `answerDirectly`, the smalltalk path, is 0.3). Zero failover events in 6 h.

**Conclusion.** Retrieval is deterministic. The residual variance is provider-level
non-determinism at temperature 0 on an MoE model. **No change in this repo fixes it.** The only
levers are passing `seed` on the answer call (if the provider honours it) or a stronger answer
model — both A/B decisions, not fixes.

## 4. What was investigated and found to be no defect

### N1 — `scopes_found: []` was not the bug I claimed
I recorded that "`scopesFound` iterates `evidence.memories` which the tool-calling path doesn't
populate", and separately that `scope` was not hydrated. **Both false**, traced in code:
- `mapMemoryRecord` (`prisma-graph-store.js:168`) sets `scope: record.scope || 'personal'`;
- `mapAgentRow` (`:107`) sets the same, so remote/`.amr` orgs match;
- all 776 memories in org `1380251c` have a non-null `scope` column;
- `scopesFound` **is** computed on the recall path's single user-facing return;
- the other returns that omit it (`:2390`, `:2412`) are **connector-write** turns that retrieve
  no memories at all — `[]` is correct there.

**The genuine gap** is smaller and different: `scopesFound` reflected only the **memory** lane,
so an answer built purely from `knowledge_segments` — exactly what a KB question hits — showed no
provenance chip. That is what D3 fixed.

### N2 — `.amr` memory counts of 0 were the truth
I diagnosed `[embedded-agent] shard open org=… live=0` as a silent-empty-shard bug and was
building toward a fix when the owner said they had **cleared** that org earlier. `stats: 0`,
empty `/api/memories` and `recall: 0` were all **correct**. The `n=98` I had compared against was
pre-clear. Retracted.

The shard **self-contention** (D4) is real and separate; I had wrongly attached these symptoms
to it.

## 6. Is `.amr` standalone for lexical?

**Engine: yes.** `amr-store.mjs` has its own `lexical()` — a token-overlap scan over shard
records, no SQL — alongside `recall()`, `hydrate()`, `graph()`, `stats()`.

**Deployed: no, deliberately.** Both lexical lanes go through Postgres.
`embedded-agent.mjs:578` records the reason: routing memory lexical through the SQL mirror makes
the two `.amr` modes rank text **identically to hybrid**, and it gains filters the shard index
cannot express — `layer`, `must_not.layer`, `known_at`, and the `valid_at` temporal snapshot.
The shard's own `lexical()` is a full scan with substring matching: no index, no stemming, no
temporal filters.

The mirror is populated (33/33 memories, 31/31 segments with `content_tsv` on the test org), so
this is a live, working choice rather than an aspiration.

**If standalone is ever wanted**, it is a flag plus a documented capability gap (ranking parity
and temporal filters lost), not a small change.

## 9. Invariants for the next session

- **A timeout is not an absence.** Any path that can fail must be able to *say* it failed;
  never let a lookup failure render as "nothing found".
- **Retrieval must never fund ranking.** Reserving budget for the reranker starved retrieval to
  ~1 ms and produced 0/5 three times.
- **Never return an empty result for a failed read.** Throw; background callers opt into
  tolerance explicitly.
- **Same dimension ≠ same vector space.** Only swap embedding links running the *same model*.
- **Measure before believing a plan's rationale.** Trigram's stated justification was wrong by
  a factor of two on the only case that mattered.
- **Read `docker exec hm-core env` before reasoning about any tunable.**
